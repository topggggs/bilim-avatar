# Архитектура v0.1

## Поток данных

1. Сотрудник входит через OIDC; сервер связывает проверенный `sub` с записью users.
2. Версия конфигурации и согласия фиксируется при создании session.
3. Браузер хранит черновик по ID пользователя и последовательно отправляет изменения. Ответы принимаются только от владельца активной сессии.
4. Submit читает сохранённые ответы, выполняет расчёт общим модулем и требует выбор при равных главном/втором качествах. В одной транзакции сохраняются результат и avatar job intent.
5. API отправляет ID аватара в Redis. Ошибка постановки переводит аватара в fallback. Повторный submit идемпотентен; jobId совпадает с ID записи.
6. Отдельный worker получает только ID, читает серверную конфигурацию, вызывает модель, проверяет изображение, сохраняет PNG в приватный S3 и обновляет статус.
7. На любой ошибке проверки/модели/storage показывается детерминированный SVG. Внутренних попыток максимум три в общем бюджете 28 секунд. Sweeper завершает оставшиеся queued/generating после 27 секунд; обновления готового изображения после дедлайна не перезаписывают fallback.
8. Профиль отдаётся только владельцу или непосредственному руководителю. Отдельные ответы не входят в DTO профиля, команды или истории. Файл также защищён проверкой роли/команды; S3-ссылка подписана на 120 секунд.

## Хранилища

`MemoryStore` используется в REST-тестах, `FileStore` — только в локальной демонстрации, `PostgresStore` — для серверного использования.

Таблицы: test_versions, app_settings, users, sessions, answers, results, recommendations_shown, avatars, audit_log. Для конфигурации и снимков применяются JSONB; связи пользователей/сессий/версий и индексы вынесены в отдельные колонки. answers не смешиваются с публичным профилем. Рекомендации фиксируются в момент результата, не пересчитываются из будущей библиотеки.

На этапе пилота store использует один PostgreSQL advisory transaction lock и транзакционную загрузку снимка состояния. Это защищает от параллельного создания сессий и превышения лимита вариантов между API/worker. Цена — сериализация операций и загрузка всего пилотного набора; это **не архитектура для большой численности**. Перед массовым запуском следует заменить адаптер целевыми SQL-запросами, блокировками строк, SQL-пагинацией аудита, миграциями с номерами и outbox-dispatcher. Внешний REST-контракт и ядро от этой замены не зависят.

FileStore пишет через временный файл и atomic rename, но не синхронизирует несколько процессов. Не запускайте несколько API или отдельный worker над одним JSON-файлом. Используйте PostgreSQL.

## Авторизация и безопасность

- OIDC confidential client: RS256/ES256, discovery/JWKS, issuer/aud/azp, обязательные exp/iat/sub, nonce/state, PKCE. Роль берётся из БД, не из браузера.
- OIDC требует HTTPS-origin и Secure-cookie. Сервер расположен за одним доверенным proxy (`trust proxy=1`); ingress должен быть единственным внешним входом, удалять входной X-Forwarded-For и устанавливать свой. Для другой топологии настройку следует изменить.
- State-changing запросы требуют точного Origin. API рассчитан на same-origin web, а не открытую cross-origin интеграцию.
- Ограничение размера JSON, schema validation, rate limit, Helmet/CSP. Лимитер процесса подходит для пилота; для нескольких API нужен общий rate-limit store на Redis.
- Локальные данные очищаются при logout. Service worker не кэширует API. Ответы в localStorage нужны для плохой связи; общие устройства требуют завершения сессии и политики рабочего места.
- Менеджер ограничен непосредственной командой. Методолог и администратор не получают HR-профили по своей роли.
- Журналируются начало/завершение теста, просмотры, изменения пользователей и методики, выбор/перегенерация аватара. Ответы и ключи в аудит не пишутся.
- Нет автоматических кадровых решений и маршрутов, принимающих такие решения.

## REST

Все пути после `/api/auth` (кроме health/mode) требуют cookie-сессии.

| Метод | Путь                           | Доступ / назначение                                                      |
| ----- | ------------------------------ | ------------------------------------------------------------------------ |
| GET   | /api/auth/mode                 | Демонстрация или OIDC                                                    |
| GET   | /api/auth/login                | Старт SSO                                                                |
| GET   | /api/auth/callback             | Проверка OIDC                                                            |
| POST  | /api/auth/logout               | Выход                                                                    |
| POST  | /api/auth/demo                 | Только локальный demo; четыре вымышленные роли                           |
| GET   | /api/me                        | Текущий пользователь                                                     |
| GET   | /api/test/config               | Активная конфигурация                                                    |
| GET   | /api/test/sessions/current     | Своя незавершённая сессия и её версия                                    |
| POST  | /api/test/sessions             | Внешность и consent=true; возврат активной сессии или проверка интервала |
| PUT   | /api/test/sessions/:id/answers | Частичное сохранение собственных ответов                                 |
| POST  | /api/test/sessions/:id/submit  | Расчёт, рекомендации, генерация; optional primary/secondary              |
| GET   | /api/profile/:userId           | Владелец / руководитель команды; без answers                             |
| GET   | /api/team                      | Непосредственная команда руководителя                                    |
| GET   | /api/avatar/:userId            | Статусы и варианты, остаток перегенераций                                |
| GET   | /api/avatars/:id/image         | Проверка доступа → SVG или подписанный S3 URL                            |
| POST  | /api/avatar/:userId/regenerate | Только свой текущий результат, не более 3 новых вариантов                |
| POST  | /api/avatars/:id/fix           | Фиксация одного своего варианта                                          |
| GET   | /api/methodology/config        | Методолог / администратор                                                |
| POST  | /api/methodology/versions      | Только методолог; новая неизменяемая версия                              |
| GET   | /api/admin/users               | Администратор                                                            |
| POST  | /api/admin/users               | Привязка sub, роли, руководителя                                         |
| GET   | /api/admin/audit               | Последние 200 записей                                                    |
| GET   | /api/learning/link?path=…      | Разрешённый путь → URL настроенного портала                              |

Ошибка: `{error, ...details}`. Неполные/неверные данные → 400, нет входа → 401, нет доступа → 403, недоступный ресурс → 404, конфликт состояния/интервала → 409.

Равенство показателей: 409 с `code: AVATAR_CHOICE_REQUIRED`, `primaryOptions`, `secondaryOptions`, `percentages`. Submit не меняет состояние до корректного выбора. Повторная отправка завершённой сессии возвращает тот же результат, не создаёт ещё одного героя.

## Эксплуатационные границы

- SSO проверен кодом и ограничениями доступа, но не реальным tenant Bilim. Нужно совместно проверить logout/срок сессии, claims и provisioning. Использован базовый RP login; refresh tokens, back-channel logout и синхронизация справочника HR не реализованы.
- Модель изображений не вызывалась с настоящим ключом; полный конвейер протестирован с mock модели. Нет утверждённых BI reference images; для их передачи через images/edits нужен следующий этап после получения эталонов. Текущие промпты единообразны и соответствуют полям ТЗ, однако художественная приёмка остаётся открытой.
- Бюджет до 30 секунд гарантирует запасной образ, а не успешную внешнюю генерацию. Автоматическая vision-проверка не даёт абсолютной гарантии отсутствия чужих персонажей или ошибок логотипа.
- Возврат к приложению без сети проверен для сохранённой оболочки и существующей вкладки/сессии. Первый вход, SSO и отправка результата требуют сети. При первом офлайн-запуске без ранее закэшированной оболочки сайт не откроется.
- Поддержаны современные Chromium и mobile viewport; реальные Safari/Samsung Internet и старые ОС ещё не проверены. Требование iOS14/Android8 требует отдельного device-пилота и, возможно, legacy polyfills. Сборка JS target=es2018 не равна подтверждённой поддержке всех Web API старого браузера.
- KZ-перевод, HR-интеграция, утверждённая политика удаления/ретенции, резервное копирование, мониторинг, нагрузочные/SLO-тесты, отказоустойчивый Redis и промышленный security-review — перед массовым запуском.
- Динамика между разными версиями выводит версию теста; статистическую сопоставимость разных редакций должен оценивать методолог.
